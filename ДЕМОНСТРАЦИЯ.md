# Практическое руководство для бригадира 
Что подготовить заранее, в каком
порядке показывать, что говорить и что делать, если что-то пошло не так.
Расчётное время демонстрации — **12–15 минут**.

---

## 0. Что подготовить заранее (сделать до пары)

1. **Docker Desktop** — запустить и дождаться, пока значок перестанет
   анимироваться. Проверка:

   ```bash
   docker info --format '{{.ServerVersion}}'
   ```

   Должна вывестись версия, например `28.3.3`. Если написано
   `Cannot connect to the Docker daemon` — Docker ещё не запустился.

2. **Поднять стенд** заранее (занимает 2–4 минуты, при преподавателе это
   делать не нужно):

   ```bash
   cd "Проект_Сервис_аренды_техники/replication"
   bash setup.sh
   ```

   В конце должно быть `Slave_IO_Running: Yes` и `Slave_SQL_Running: Yes`
   по всем узлам.

3. **Открыть заранее в отдельных окнах:**
   - отчёт: `Отчёт_Проектирование_РБД_CampusRent.pdf` (36 страниц) — так
     надёжнее, чем `.docx`, вёрстка не поедет;
   - презентацию: `presentation/Презентация_Проект_РБД_CampusRent.pptx`
     (25 слайдов, с логотипом и синими заголовками) или её PDF-версию;
   - терминал в каталоге `Проект_Сервис_аренды_техники`.

4. **Проверить перед показом один раз** (30 секунд):

   ```bash
   cd "Проект_Сервис_аренды_техники/replication"
   docker exec mysql-consol mysql -uroot -ppassword --default-character-set=utf8mb4 \
     -e "SHOW SLAVE STATUS\G" | grep -E "Channel_Name|Running" | head -12
   ```

   Ожидается шесть строк `Running: Yes` (каналы `hq`, `spb`, `kzn` плюс
   каналы узлов).

## 1. Порядок показа (сценарий)

### Шаг 1. Постановка задачи — слайды 1–4 (1 минута)

Открываем презентацию. Говорим: компания сдаёт вузам технику в аренду, есть
центральный офис и филиалы; данные и их потребители распределены
географически, поэтому нужна именно **распределённая** БД, а не один сервер.

### Шаг 2. Проектирование — слайды 5–12 (4 минуты)

- Слайд 5 — схема сети компании.
- **Слайд 6 — нотация связей «вороньи лапки»**: одна черта — «один»,
  воронья лапка — «многие». Если спросят «где кардинальности связей» —
  это тот слайд.
- Слайды 7–8 — ER-диаграммы в этой нотации: НСИ с клиентами и персоналом,
  затем техника с арендой и сервисом (все 22 сущности).
- Слайд 9 — схема БД по подсистемам: **22 отношения**, приведённые к **4НФ**;
  детальные схемы отношений с атрибутами — в отчёте, приложение А
  (рисунки 9–11).
- **Слайд 10 — схема фрагментации**, ключевой слайд: цвета показывают разные
  методы поддержки распределённости, стрелки — направление передачи данных.
- Слайд 11 — таблица «какой метод для какой группы таблиц».
- **Слайд 12 — триггеры**: 18 триггеров, сгруппированных по реализуемым
  правилам.

### Шаг 3. Стенд репликации — слайд 13 (1 минута)

Говорим: стенд — четыре контейнера MySQL 8.0 в Docker (ЦО, два филиала, узел
консолидации), между ними **шесть каналов репликации**. Дальше показываем
живьём.

### Шаг 4. Три механизма репликации вживую (4 минуты)

Все команды выполняются из каталога `replication`. Параметр
`--default-character-set=utf8mb4` в каждой команде обязателен.

**РОК — репликация с основной копией (изменение НСИ из ЦО в филиалы):**

```bash
docker exec mysql-master mysql -uroot -ppassword --default-character-set=utf8mb4 campusrent \
  -e "UPDATE tariffs SET TAR_PRICE = TAR_PRICE + 100 WHERE TAR_ID = 2011;"

docker exec mysql-slave mysql -uroot -ppassword --default-character-set=utf8mb4 campusrent \
  -e "SELECT TAR_ID, TAR_PRICE FROM tariffs WHERE TAR_ID = 2011;"
```

Что сказать: изменили тариф в центральном офисе — в филиале он уже новый.

**РБОК — репликация без основной копии (изменение из филиала):**

```bash
docker exec mysql-slave mysql -uroot -ppassword --default-character-set=utf8mb4 campusrent -e \
  "INSERT INTO universities (UN_ID,UN_NAME,UN_SHORT,UN_INN,UN_ADDRESS,UN_CITY,UN_BR)
   VALUES (9099,'Тестовый университет','ТЕСТВУЗ','9900000099','ул. Тестовая, 1','Санкт-Петербург','SPB');"

docker exec mysql-master  mysql -uroot -ppassword --default-character-set=utf8mb4 campusrent \
  -e "SELECT UN_ID, UN_SHORT FROM universities WHERE UN_ID = 9099;"
docker exec mysql-slave2  mysql -uroot -ppassword --default-character-set=utf8mb4 campusrent \
  -e "SELECT UN_ID, UN_SHORT FROM universities WHERE UN_ID = 9099;"
```

Что сказать: вуз завели в филиале — он появился и в центральном офисе, **и во
втором филиале** (в MySQL 8.0 `log_replica_updates` включён по умолчанию,
поэтому приёмник передаёт событие дальше).

**РКД — консолидация (данные филиала попадают в сводную копию):**

```bash
docker exec mysql-slave mysql -uroot -ppassword --default-character-set=utf8mb4 campusrent -e \
  "INSERT INTO equipment_units (EQ_ID,EQ_INV,EQ_MOD,EQ_BR,EQ_STATUS,EQ_COND,EQ_ACQUIRE)
   VALUES (909900,'SPB-909900',404,'SPB','свободна',2,'2026-09-01');"

docker exec mysql-consol mysql -uroot -ppassword --default-character-set=utf8mb4 campusrent \
  -e "SELECT EQ_ID, EQ_INV, EQ_BR FROM equipment_units WHERE EQ_ID = 909900;"
```

### Шаг 5. Распределённая транзакция (главный козырь) — 3 минуты

```bash
bash distributed_booking.sh
```

Что происходит и что говорить по ходу вывода скрипта:

1. скрипт сам находит модель, которой в филиале-заказчике мало, а в
   филиале-владельце достаточно;
2. **фаза 1**: на узле-владельце выполняется `XA PREPARE` — экземпляр
   забронирован, но **изменение не видно другим сеансам** (в выводе это
   отдельно показано: статус остаётся `свободна`);
3. на узле-инициаторе создаётся заявка — тоже `XA PREPARE`, в другом сеансе
   заявки ещё нет;
4. `XA RECOVER` показывает обе подготовленные транзакции;
5. **точка фиксации** — `XA COMMIT` на обоих узлах;
6. проверка: экземпляр в статусе `бронь`, заявка создана, изменение видно в
   консолидированной копии;
7. **негативная проверка**: повторная попытка забронировать тот же экземпляр
   возвращает `NOT_FREE` и откатывается — двойное бронирование невозможно;
8. в конце — проверка, что все шесть каналов репликации остались живы.

Если спросят «почему транзакция инициатора не реплицируется» — ответ:
XA-транзакции в MySQL несовместимы с фильтрами репликации (ошибка 3898),
поэтому участником выбран узел, изменения которого принимает консолидация, а
транзакция инициатора выполняется локально; атомарность обеспечивают фазы XA,
а не репликация. Это разобрано в отчёте и в шапке скрипта.

## 3. Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| `Cannot connect to the Docker daemon` | Запустить Docker Desktop, подождать 30–60 секунд |
| `port is already allocated` | Порт занят: `docker compose down -v` и снова `bash setup.sh` |
| `Slave_SQL_Running: No` | Посмотреть `Last_Error` в `SHOW SLAVE STATUS`; чаще всего канал остановлен после повторного запуска DDL |
| `ERROR 1406: Data too long for column 'EQ_STATUS'` | Забыт параметр `--default-character-set=utf8mb4` |
| Данные «не сошлись» с отчётом | Стенд изменён демонстрацией. Вернуть исходное состояние: `docker compose down -v && bash setup.sh` |
| Совсем нет времени | Показывать презентацию и протоколы в `results/`; распределённую транзакцию — по протоколу `results/distributed_booking_log.md` |

**Полный сброс стенда в исходное состояние** (1–3 минуты):

```bash
cd "Проект_Сервис_аренды_техники/replication"
docker compose down -v
bash setup.sh
```

## 4. Шпаргалка: вероятные вопросы и короткие ответы

| Вопрос | Ответ |
|---|---|
| Почему база распределённая, а не один сервер? | Данные и потребители распределены: техника лежит в филиале, заявки и выдача происходят там же; филиал должен работать при обрыве связи с ЦО. Плюс нужна централизованная НСИ и сводная отчётность |
| Почему горизонтальная фрагментация, а не вертикальная? | Вертикальная потребовала бы распределённых соединений по каждому запросу; горизонтальная по филиалу даёт автономность филиала при небольших объёмах данных |
| Какие методы поддержки распределённости применены? | Репликация с основной копией (НСИ), без основной копии (клиенты), с консолидацией (техника, заявки, договоры, платежи, обслуживание), фрагментация по филиалам, распределённые запросы и распределённая транзакция |
| Почему для НСИ выбрана репликация с основной копией? | Справочники формируются централизованно, меняются редко, важна согласованность на всех узлах |
| Почему для клиентов — без основной копии? | Вуз можно зарегистрировать в любом филиале, источник изменений не един |
| Сколько каналов репликации? | Шесть: два РОК (ЦО → филиалы), один РБОК (филиал → ЦО), три канала консолидации (`hq`, `spb`, `kzn`) |
| Как реализована распределённая транзакция? | Протокол двухфазной фиксации на XA-транзакциях MySQL: `XA PREPARE` на двух узлах, затем `XA COMMIT`; при сбое — откат. Скрипт `replication/distributed_booking.sh` |
| Что происходит при конфликте репликации? | Конфликты возможны только для клиентов: слияние по уникальному ИНН, приоритет более позднего изменения, логическое удаление |
| Почему в схеме 22 отношения? | 18 сущностей предметной области плюс 4 справочника НСИ (статусы заявок, способы оплаты, виды обслуживания, степени состояния) |
| Что не реализовано? | Перенос техники между филиалами (РТ-2) и автоматический рабочий поток согласования заявок — спроектированы и вынесены в перспективу; это указано в отчёте, п. 7.4.2 |
| Как проверялась целостность? | 11 контрольных примеров в `tools/integrity_tests.sql`; все 11 дали ожидаемый результат — `results/integrity_tests.md` |
