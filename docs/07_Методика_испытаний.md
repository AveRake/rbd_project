# 7. Методика испытаний (контрольные примеры)

Контрольные примеры демонстрируют работоспособность как реляционной БД
(ограничения целостности, триггеры, представления), так и распределённой
(репликация, консолидация, распределённые запросы и транзакции).

## 7.1. Загрузка данных

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Выполнить `sql/01_schema.sql` | создана БД `campusrent` и 22 таблицы |
| 2 | Выполнить `sql/02_reference_data.sql` | заполнены справочники НСИ |
| 3 | Выполнить `sql/03_test_data.sql` | загружены тестовые данные (десятки–сотни записей) |
| 4 | Выполнить `sql/04_views.sql`, `05_triggers.sql`, `06_indexes.sql` | созданы представления, триггеры, индексы |
| 5 | Выполнить `sql/07_users_grants.sql` | созданы роли и назначены права |

## 7.2. Проверка ограничений целостности

| № | Контрольный пример | Ожидаемый результат |
|---|---|---|
| 1 | Вставить заявку с филиалом, отличным от `universities.UN_BR` | ошибка триггера `trg_req_check_branch` |
| 2 | Вставить позицию заявки с тарифом другой модели | ошибка триггера `trg_rit_check_tariff` |
| 3 | Выдать один экземпляр двум договорам на пересекающийся период | ошибка триггера `trg_rental_check_overlap` |
| 4 | Выдать экземпляр со статусом 'аренда' | ошибка триггера `trg_rental_check_available` |
| 5 | Выдать экземпляр с моделью, не соответствующей позиции | ошибка триггера `trg_rental_check_available` |
| 6 | Вставить тариф с датой окончания раньше даты начала | ошибка check-ограничения |
| 7 | Вставить представителя с паспортом, уже существующим в БД | ошибка уникальности |
| 8 | После успешной выдачи экземпляр получает статус 'аренда' | статус изменился автоматически |
| 9 | После возврата экземпляр получает статус 'свободна' и фиксируется состояние | статус и состояние обновлены |
| 10 | Сумма позиций заявки ≠ `REQ_SUM` | ошибка триггера `trg_request_check_sum` |

## 7.3. Проверка представлений и отчётных запросов

| № | Запрос | Ожидаемый результат |
|---|---|---|
| 1 | `v_available_equipment` | список свободной техники с указанием филиала и модели |
| 2 | `v_current_rentals` | невозвращённые выдачи с арендатором и сроком |
| 3 | `v_overdue_rentals` | выдачи с просроченной датой возврата |
| 4 | `v_branch_load` | загрузка парка по каждому филиалу (число экземпляров по статусам) |
| 5 | `v_consolidated_fleet` | сводный парк по всем филиалам |
| 6 | Отчёт «выручка по филиалам» | суммы платежей по филиалам |
| 7 | Отчёт «популярные модели» | рейтинг моделей по числу выдач |
| 8 | Отчёт «затраты на ремонт» | суммы затрат по видам работ и филиалам |

## 7.4. Проверка распределённых механизмов

| № | Сценарий | Ожидаемый результат |
|---|---|---|
| 1 | РОК: изменение тарифа на ЦО | изменение через несколько секунд появляется в филиале |
| 2 | РБОК: добавление вуза в филиале | запись появляется в ЦО и других филиалах |
| 3 | РКД: добавление экземпляра техники в филиале | запись появляется в консолидированной копии ЦО |
| 4 | Распределённый запрос: поиск модели по всем филиалам | собраны сведения из всех ответивших узлов |
| 5 | Распределённая транзакция: бронирование в другом филиале | экземпляр забронирован атомарно; повторная бронь невозможна |
| 6 | Распределённая транзакция: перенос техники | экземпляр сменил филиал, создана запись в `transfers` |
| 7 | Рабочий поток: согласование заявки | статус заявки изменён согласованно в филиале и ЦО |
| 8 | Отказ узла при распределённом запросе | запрос завершается успешно по остальным узлам |

## 7.5. Форма протокола испытаний

Результаты прогонов сохраняются в каталоге `results/` в виде markdown-файлов:

| Файл | Содержание |
|---|---|
| `results/query_results.md` | результаты отчётных запросов (таблицы) |
| `results/integrity_tests.md` | результаты проверки ограничений целостности |
| `results/replication_log.md` | журнал проверки репликации |
| `results/graphs/` | графики для итогового отчёта |
