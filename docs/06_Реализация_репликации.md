# 6. Реализация репликации

Раздел описывает стенд распределённой БД на базе MySQL 8.0 в Docker **по
фактическому состоянию файлов** каталога `replication/`. Все конфигурации и
команды, приведённые ниже, скопированы из рабочих файлов стенда, а не из
проектного замысла; расхождения проекта и реализации вынесены в п. 6.7.

## 6.1. Состав стенда

Стенд описан в `replication/docker-compose.yml`, сеть — `campusnet` (bridge),
образ — официальный `mysql:8.0`, пароль `root` на всех узлах — `password`.

| Контейнер | Роль | Порт на хосте | server-id | Репликация |
|---|---|---|---|---|
| `mysql-master` | ЦО (`hq`), источник НСИ | 3306 | 1 | master для РОК; **slave** для РБОК |
| `mysql-slave` | филиал Санкт-Петербург (`spb`) | 3307 | 2 | slave РОК; источник для РБОК и РКД |
| `mysql-slave2` | филиал Казань (`kzn`) | 3309 | 4 | slave РОК; источник для РКД |
| `mysql-consol` | узел консолидации | 3308 | 3 | slave РКД (три канала) |

Нумерация `server-id` (1, 2, 4, 3) соответствует файлам конфигурации;
`server-id` узла Казань — 4, а не 3, потому что 3 занят узлом консолидации.
Именованных томов у контейнеров нет: данные лежат в слое контейнера, поэтому
повторный запуск стенда выполняется после `docker compose down -v`.

## 6.2. Общие параметры конфигурации узлов

Во всех четырёх файлах (`master.cnf`, `slave.cnf`, `slave2.cnf`, `consol.cnf`)
заданы одинаковые базовые параметры:

```ini
[mysqld]
log-bin
binlog-do-db  = campusrent
binlog-format = ROW
secure-file-priv = NULL
default-authentication-plugin = mysql_native_password
pid-file = /var/run/mysqld/mysqld.pid
socket   = /var/run/mysqld/mysqld.sock
datadir  = /var/lib/mysql

# В образе локаль C, поэтому клиент mysql внутри контейнера нужно явно
# перевести в utf8mb4: иначе русский текст искажается, а вставка в
# VARCHAR(12) (например, EQ_STATUS) падает с ошибкой 1406.
[client]
default-character-set = utf8mb4
```

Почему так:

- **`log-bin` на всех узлах** — бинарный журнал нужен не только источнику:
  узел-приёмник тоже пишет свой журнал, потому что он является источником для
  следующего звена (ЦО → консолидация, филиал → консолидация).
- **`binlog-format = ROW`** — реплицируются изменения строк, а не текст команд.
  Это принципиально для распределённой транзакции `XA` и для триггеров:
  на приёмнике повторно не выполняются триггеры источника.
- **`binlog-do-db = campusrent`** — в журнал попадают изменения только этой БД.
  Все скрипты `sql/` начинаются с `USE campusrent;`, поэтому фильтр не мешает.
- **`secure-file-priv = NULL`** — импорт/экспорт файлов запрещён; для репликации
  этот параметр не требуется, он оставлен из соображений безопасности.
- Параметры `read_only`/`super_read_only` **не используются**: узлы-приёмники
  одновременно являются источниками (РБОК, РКД), а на узле консолидации
  выполняется загрузка снимка.

> **Важно (MySQL 8.0).** Параметр `log_replica_updates` (в 5.7 —
> `log_slave_updates`) в MySQL 8.0 **включён по умолчанию**, то есть узел
> записывает в свой бинарный журнал и те события, которые сам получил от
> источника. Проверено на стенде: `SELECT @@log_replica_updates` → `1` на всех
> четырёх узлах. Практические следствия:
> 1) РБОК действительно доходит до остальных филиалов транзитом через ЦО;
> 2) **DDL-скрипты нельзя повторно запускать на отдельном узле работающего
>    стенда** — созданный объект попадает в журнал, разносится по каналам, и узел,
>    где такой объект уже есть, останавливает канал с ошибкой 1304
>    `... already exists`. Поэтому вся схема, данные, представления, триггеры,
>    индексы и роли загружаются один раз на все узлы до включения репликации
>    (шаг 3 `setup.sh`).

## 6.3. Репликация с основной копией (РОК)

Справочники НСИ формируются в ЦО и распространяются в филиалы. Источник —
`mysql-master`, приёмники — `mysql-slave` и `mysql-slave2`.

**`master.cnf`** (узел ЦО) — источник; собственные фильтры приёма у него только
для РБОК (см. п. 6.4):

```ini
[mysqld]
server-id = 1
replicate-do-table = campusrent.universities
replicate-do-table = campusrent.departments
replicate-do-table = campusrent.representatives
```

**`slave.cnf`** (филиал СПб) — приёмник; применяет **14 таблиц**: 11 справочных
и 3 таблицы клиентов (последние — уже для РБОК):

```ini
[mysqld]
server-id = 2
replicate-do-table = campusrent.branches
replicate-do-table = campusrent.categories
replicate-do-table = campusrent.models
replicate-do-table = campusrent.model_components
replicate-do-table = campusrent.model_purposes
replicate-do-table = campusrent.tariffs
replicate-do-table = campusrent.request_statuses
replicate-do-table = campusrent.payment_methods
replicate-do-table = campusrent.maintenance_types
replicate-do-table = campusrent.condition_grades
replicate-do-table = campusrent.employees
replicate-do-table = campusrent.universities
replicate-do-table = campusrent.departments
replicate-do-table = campusrent.representatives
```

**`slave2.cnf`** (филиал Казань) полностью совпадает с `slave.cnf`, отличается
только `server-id = 4`.

Механизм: ЦО пишет изменения НСИ в свой бинарный журнал, а фильтры
`replicate-do-table` **на стороне приёмника** определяют, какие таблицы
применять. Операционные таблицы (`equipment_units`, `requests`, `contracts`,
`rentals`, `payments`, `maintenance`, `transfers`) в список не входят, поэтому
на филиалы НСИ приходит, а операционные данные филиалов — нет.

## 6.4. Репликация без основной копии (РБОК)

Таблицы клиентов (`universities`, `departments`, `representatives`) должны
изменяться в любом узле. В стенде это реализовано парой встречных каналов:

- в `master.cnf` (ЦО) перечислены эти три таблицы в `replicate-do-table` —
  ЦО является приёмником изменений из филиала СПб;
- в `slave.cnf` и `slave2.cnf` те же таблицы тоже перечислены — филиалы
  принимают изменения от ЦО.

**Как изменение расходится по сети.** Благодаря `log_replica_updates = 1`
событие, применённое узлом-приёмником, записывается в его собственный
бинарный журнал и уходит дальше. Поэтому вставка вуза в филиале СПб доходит
не только до ЦО, но и до второго филиала:

```
spb --(канал РБОК: slave -> master)--> hq --(РОК: master -> slave2)--> kzn
```

Проверено на стенде: `INSERT` вуза с `UN_ID = 9099` в филиале СПб появился и в
ЦО, и в Казани (см. `results/replication_log.md`, п. 3).

**Ограничение.** Схема не является полносвязной: у `mysql-slave2` (Казань) нет
собственного исходящего канала РБОК, поэтому изменения, сделанные **в Казани**,
в другие узлы не уходят — они доступны только локально и (для операционных
таблиц) в консолидированной копии. Для демонстрации асинхронного
распространения без основной копии достаточно пары «ЦО ↔ филиал СПб»; при
развитии стенда каждому филиалу нужен свой встречный канал с ЦО.

## 6.5. Репликация с консолидацией (РКД)

Узел `mysql-consol` собирает операционные данные всех узлов в единую копию.
Он подключается **тремя каналами** — по одному к каждому источнику.

**`consol.cnf`**:

```ini
[mysqld]
server-id = 3
replicate-do-table = campusrent.equipment_units
replicate-do-table = campusrent.transfers
replicate-do-table = campusrent.requests
replicate-do-table = campusrent.request_items
replicate-do-table = campusrent.contracts
replicate-do-table = campusrent.rentals
replicate-do-table = campusrent.payments
replicate-do-table = campusrent.maintenance
replicate-wild-ignore-table = campusrent.%bck%
```

Каналы настраиваются в `replication/setup.sh` (шаг 5):

```sql
CHANGE MASTER TO MASTER_HOST='mysql-master',  ... FOR CHANNEL 'hq';
CHANGE MASTER TO MASTER_HOST='mysql-slave',   ... FOR CHANNEL 'spb';
CHANGE MASTER TO MASTER_HOST='mysql-slave2',  ... FOR CHANNEL 'kzn';
START SLAVE FOR CHANNEL 'hq';
START SLAVE FOR CHANNEL 'spb';
START SLAVE FOR CHANNEL 'kzn';
```

Итого в стенде работают **шесть каналов репликации**:

| Канал | Источник → приёмник | Что переносится | Метод |
|---|---|---|---|
| РОК-1 | `mysql-master` → `mysql-slave` | 11 таблиц НСИ | с основной копией |
| РОК-2 | `mysql-master` → `mysql-slave2` | 11 таблиц НСИ | с основной копией |
| РБОК | `mysql-slave` → `mysql-master` | 3 таблицы клиентов | без основной копии |
| РКД `hq` | `mysql-master` → `mysql-consol` | 8 операционных таблиц | консолидация |
| РКД `spb` | `mysql-slave` → `mysql-consol` | 8 операционных таблиц | консолидация |
| РКД `kzn` | `mysql-slave2` → `mysql-consol` | 8 операционных таблиц | консолидация |

## 6.6. Назначение файлов каталога `replication/`

| Файл | Назначение |
|---|---|
| `docker-compose.yml` | четыре контейнера MySQL 8.0, сеть, порты, монтирование конфигов |
| `master.cnf`, `slave.cnf`, `slave2.cnf`, `consol.cnf` | параметры серверов и фильтры репликации |
| `master.sql`, `slave.sql`, `slave2.sql`, `consol.sql` | **только** создание пользователей репликации (`repl`, `replslave`, `replconsol`) и выдача `REPLICATION SLAVE`; подключаются как `docker-entrypoint-initdb.d/00_replication_user.sql` |
| `setup.sh` | развёртывание стенда: запуск, загрузка снимка, фиксация позиций, настройка всех шести каналов, печать состояния |
| `distributed_booking.sh` | распределённая транзакция РТ-1 (межфилиальное бронирование, 2PC через XA) |
| `backup/` | точка монтирования для `mysqldump` на узле ЦО (см. `05_Физическое_проектирование.md`, п. 5.7); каталог пуст, резервное копирование выполняется по регламенту вручную или по cron |

Команды `CHANGE MASTER TO` намеренно вынесены в `setup.sh`, а не в `.sql`-файлы:
позиции бинарных журналов становятся известны **только после** загрузки снимка
данных, а `.sql`-файлы в `docker-entrypoint-initdb.d` выполняются до неё.

### 6.6.1. Порядок работы `setup.sh`

1. `docker compose up -d` — подъём четырёх контейнеров;
2. ожидание готовности узлов (`mysqladmin ping`, до 60 попыток по 2 с);
3. **загрузка одинакового снимка** `sql/01…07` во все четыре узла;
4. фиксация текущих позиций бинарных журналов ЦО, СПб и Казани
   (`SHOW MASTER STATUS`);
5. сброс прежних каналов (`STOP SLAVE`, `RESET SLAVE ALL`, для консолидации —
   `FOR CHANNEL ...`) и включение всех шести каналов от зафиксированных
   позиций;
6. печать `SHOW SLAVE STATUS` по узлам, у которых есть каналы.

Позиции фиксируются **после** загрузки данных: репликация начинается «с
текущего момента» и не пытается повторно применить уже загруженный снимок
(иначе приёмник упал бы на дубликатах первичных ключей).

## 6.7. Особенности и ограничения реализации

Ниже — то, что важно знать при защите: расхождения между проектным замыслом
(`04_Схема_фрагментации.md`) и фактической реализацией стенда.

1. **Способ репликации — непрерывный, а не «раз в сутки».** В проекте
   (п. 4.2, 4.5) для НСИ и консолидации выбраны моментальные снимки с полной
   регенерацией раз в сутки. В стенде для наглядности реализована
   **непрерывная асинхронная репликация** на основе бинарного журнала
   (`binlog-format = ROW`): тот же эффект распространения данных наблюдается
   сразу, без ожидания регламентного окна. Схема со снимками остаётся
   проектным решением для промышленного варианта (меньше трафика при редких
   изменениях НСИ).
2. **Совпадение первичных ключей при консолидации.** Все 22 отношения имеют
   одностолбцовые суррогатные первичные ключи (`EQ_ID`, `REQ_ID`, …), а новые
   ключи вычисляются как `MAX(...) + 1` в пределах узла. В стенде коллизий нет,
   потому что все узлы получают **один и тот же снимок** и добавляют записи
   только через демонстрационные сценарии. В промышленном варианте нужны либо
   диапазоны значений, закреплённые за узлами, либо составной ключ
   `(ID, узел-источник)` со служебным полем-признаком. **В текущей схеме такие
   поля отсутствуют** — это осознанное упрощение учебного стенда.
3. **Ограничения внешних ключей в консолидированной копии.** Поскольку снимок
   схемы загружается на узел консолидации целиком, все внешние ключи на месте,
   а фильтры `replicate-do-table` ограничивают только состав **строк**. Вариант
   «консолидированная копия без части таблиц», где ограничения `FOREIGN KEY`
   пришлось бы снимать, в стенде не используется.
4. **DDL и репликация.** Из-за `log_replica_updates = 1` любые DDL-скрипты
   (`sql/01`, `04`, `05`, `06`, `07`) допустимо выполнять только до включения
   каналов. Повторный запуск, например, `sql/06_indexes.sql` на одном узле
   работающего стенда останавливает каналы с ошибкой 1304.
5. **Безопасность.** Пользователи репликации используют
   `mysql_native_password` и пароль `password`, TLS для каналов не настроен,
   `secure-file-priv = NULL` выставлен без необходимости. Для учебного стенда
   это допустимо, для промышленного — нет.
6. **`replication/backup/` пуст.** Стратегия резервного копирования описана в
   `05_Физическое_проектирование.md` (п. 5.7), но ни cron-задания, ни скрипта,
   ни дампов в каталоге нет.

## 6.8. Проверка работоспособности

Команды выполняются из каталога `replication`. Параметр
`--default-character-set=utf8mb4` обязателен (см. п. 6.2).

**Состояние каналов:**

```bash
docker exec mysql-slave  mysql -uroot -ppassword --default-character-set=utf8mb4 \
  -e "SHOW SLAVE STATUS\G" | grep -E "Master_Host|Running|Last_Error"
docker exec mysql-consol mysql -uroot -ppassword --default-character-set=utf8mb4 \
  -e "SHOW SLAVE STATUS\G" | grep -E "Channel_Name|Master_Host|Running|Last_Error"
```

Ожидается `Slave_IO_Running: Yes` и `Slave_SQL_Running: Yes` для всех шести
каналов; поле `Last_Error` должно быть пустым.

**РОК** — изменение НСИ в ЦО должно появиться в филиале:

```bash
docker exec mysql-master mysql -uroot -ppassword --default-character-set=utf8mb4 campusrent \
  -e "UPDATE tariffs SET TAR_PRICE = TAR_PRICE + 100 WHERE TAR_ID = 2011;"
docker exec mysql-slave  mysql -uroot -ppassword --default-character-set=utf8mb4 campusrent \
  -e "SELECT TAR_ID, TAR_PRICE FROM tariffs WHERE TAR_ID = 2011;"
```

**РБОК** — вуз, добавленный в филиале, должен появиться в ЦО **и в другом
филиале**:

```bash
docker exec mysql-slave mysql -uroot -ppassword --default-character-set=utf8mb4 campusrent -e \
  "INSERT INTO universities (UN_ID,UN_NAME,UN_SHORT,UN_INN,UN_ADDRESS,UN_CITY,UN_BR)
   VALUES (9099,'Тестовый университет','ТЕСТВУЗ','9900000099','ул. Тестовая, 1','Санкт-Петербург','SPB');"
docker exec mysql-master  mysql -uroot -ppassword --default-character-set=utf8mb4 campusrent \
  -e "SELECT UN_ID, UN_SHORT FROM universities WHERE UN_ID = 9099;"
docker exec mysql-slave2  mysql -uroot -ppassword --default-character-set=utf8mb4 campusrent \
  -e "SELECT UN_ID, UN_SHORT FROM universities WHERE UN_ID = 9099;"
```

**РКД** — данные филиала должны появиться в консолидированной копии:

```bash
docker exec mysql-slave  mysql -uroot -ppassword --default-character-set=utf8mb4 campusrent -e \
  "INSERT INTO equipment_units (EQ_ID,EQ_INV,EQ_MOD,EQ_BR,EQ_STATUS,EQ_COND,EQ_ACQUIRE)
   VALUES (909900,'SPB-909900',404,'SPB','свободна',2,'2026-09-01');"
docker exec mysql-consol mysql -uroot -ppassword --default-character-set=utf8mb4 campusrent \
  -e "SELECT EQ_ID, EQ_INV, EQ_BR FROM equipment_units WHERE EQ_ID = 909900;"
```

**Распределённая транзакция (РТ-1)** — межфилиальное бронирование по протоколу
двухфазной фиксации; скрипт сам выбирает дефицитную в Казани модель, готовит
транзакцию на двух узлах, фиксирует её, проверяет результат в
консолидированной копии и демонстрирует откат при повторном бронировании:

```bash
bash distributed_booking.sh
```

Результаты проверок заносятся в `results/replication_log.md`, методика —
в `07_Методика_испытаний.md`.
