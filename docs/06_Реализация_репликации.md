# 6. Реализация репликации

Раздел описывает настройку стенда распределённой БД на базе MySQL 8.0 в
Docker. Все файлы находятся в каталоге `replication/`.

## 6.1. Состав стенда

| Контейнер | Роль | Порт на хосте | server-id |
|---|---|---|---|
| `mysql-master` | ЦО (`hq`), источник НСИ | 3306 | 1 |
| `mysql-slave` | филиал (`spb`), приёмник НСИ | 3307 | 2 |
| `mysql-consol` | узел консолидации | 3308 | 3 |

Для имитации второго филиала можно добавить ещё один контейнер (`mysql-slave2`,
порт 3309, `server-id=4`) — он настраивается аналогично первому.

## 6.2. Репликация с основной копией (РОК)

Таблицы группы A (НСИ) реплицируются из ЦО (master) во филиалы (slave).

**`master.cnf`** (узел ЦО):
```ini
[mysqld]
server-id=1
log-bin
binlog-do-db = campusrent
pid-file    = /var/run/mysqld/mysqld.pid
socket      = /var/run/mysqld/mysqld.sock
datadir     = /var/lib/mysql
secure-file-priv = NULL
```

**`slave.cnf`** (филиал):
```ini
[mysqld]
server-id=2
log-bin
binlog-do-db = campusrent
replicate-do-table = campusrent.categories
replicate-do-table = campusrent.models
replicate-do-table = campusrent.model_components
replicate-do-table = campusrent.model_purposes
replicate-do-table = campusrent.tariffs
replicate-do-table = campusrent.request_statuses
replicate-do-table = campusrent.payment_methods
replicate-do-table = campusrent.maintenance_types
replicate-do-table = campusrent.condition_grades
replicate-do-table = campusrent.branches
replicate-do-table = campusrent.employees
pid-file    = /var/run/mysqld/mysqld.pid
socket      = /var/run/mysqld/mysqld.sock
datadir     = /var/lib/mysql
secure-file-priv = NULL
```

**`master.sql`** — создание пользователя репликации на ЦО:
```sql
CREATE USER 'repl'@'%' IDENTIFIED BY 'password';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';
```

**`slave.sql`** — подключение филиала к ЦО:
```sql
CHANGE MASTER TO
  MASTER_HOST='mysql-master',
  MASTER_USER='repl',
  MASTER_PASSWORD='password',
  GET_MASTER_PUBLIC_KEY=1;
START SLAVE;
```

> В MySQL 8.0 команда `CHANGE MASTER TO` поддерживается. В MySQL 8.4 она
> заменена на `CHANGE REPLICATION SOURCE TO ... SOURCE_HOST=...`. Скрипты даны
> для версии 8.0 в соответствии с методическими указаниями.

## 6.3. Репликация без основной копии (РБОК)

Таблицы группы B (`universities`, `departments`, `representatives`) должны
изменяться на любом узле и распространяться на все остальные. Для этого:

1. на **каждом** узле для этих таблиц включается `log-bin`;
2. на каждом узле создаётся пользователь репликации (`repl`);
3. каждый узел подключается как slave к остальным узлам, но реплицирует
   **только таблицы группы B** (`replicate-do-table`);
4. во избежание зацикливания репликации используются `server-id` и
   фильтры по таблицам, а также признак источника в служебном поле.

Таким образом реализуется асинхронное распространение изменений без основной
копии: любая запись, добавленная в филиале `spb`, попадает в ЦО и другие
филиалы.

## 6.4. Репликация с консолидацией (РКД)

Узел `mysql-consol` подключается каналами к каждому филиалу и собирает их
фрагменты.

**`consol.cnf`**:
```ini
[mysqld]
server-id=3
log-bin
binlog-do-db = campusrent
replicate-do-table = campusrent.equipment_units
replicate-do-table = campusrent.transfers
replicate-do-table = campusrent.requests
replicate-do-table = campusrent.request_items
replicate-do-table = campusrent.contracts
replicate-do-table = campusrent.rentals
replicate-do-table = campusrent.payments
replicate-do-table = campusrent.maintenance
pid-file    = /var/run/mysqld/mysqld.pid
socket      = /var/run/mysqld/mysqld.sock
datadir     = /var/lib/mysql
secure-file-priv = NULL
```

**`consol.sql`** — подключение двух каналов (к ЦО и к филиалу):
```sql
CHANGE MASTER TO MASTER_HOST='mysql-master', MASTER_USER='repl',
  MASTER_PASSWORD='password', GET_MASTER_PUBLIC_KEY=1 FOR CHANNEL 'hq';
CHANGE MASTER TO MASTER_HOST='mysql-slave', MASTER_USER='repl',
  MASTER_PASSWORD='password', GET_MASTER_PUBLIC_KEY=1 FOR CHANNEL 'spb';
START SLAVE FOR CHANNEL 'hq';
START SLAVE FOR CHANNEL 'spb';
```

## 6.5. Проблемы консолидации и их решения

**Проблема 1 — совпадение первичных ключей.** Записи, добавленные в разных
филиалах, могут получить одинаковые `EQ_ID`, `REQ_ID` и т. п. Решение (выбрано
для проекта): **составной первичный ключ `(ID, узел)`** — к суррогатному ключу
добавляется идентификатор узла-источника. Альтернативы: разные диапазоны
значений ключей для узлов (например, `spb` — 1 000 000…, `kzn` — 2 000 000…).

**Проблема 2 — внешние ключи на отсутствующие таблицы.** В консолидированной
копии присутствуют не все таблицы (например, НСИ может храниться в ЦО
отдельно). Поэтому в консолидированной копии ограничения `FOREIGN KEY` на
отсутствующие таблицы снимаются (поля остаются, ограничение — нет).

**Проблема 3 — согласованность во времени.** Консолидация выполняется раз в
сутки; данные в ЦО актуальны «на конец суток». Для оперативной работы
используются локальные данные филиалов.

## 6.6. Проверка работоспособности репликации

Порядок проверки (команды приведены в `replication/README.md`):

1. Запустить стенд: `docker compose up -d`.
2. Подключиться к master (порт 3306), создать БД и таблицы, загрузить НСИ.
3. Подключиться к slave (порт 3307) и убедиться, что НСИ появилась.
4. Изменить НСИ на master (`UPDATE tariffs ...`) и убедиться, что изменение
   отразилось на slave — **это демонстрация РОК**.
5. Добавить вуз на slave (`INSERT INTO universities ...`) и убедиться, что
   запись появилась на master — **это демонстрация РБОК**.
6. Добавить экземпляр техники на slave и убедиться, что запись появилась на
   узле консолидации (`consol`, порт 3308) — **это демонстрация РКД**.
7. Проверить статус репликации: `SHOW SLAVE STATUS\G` (значение
   `Slave_IO_Running` и `Slave_SQL_Running` должно быть `Yes`).

Формы протокола испытаний приведены в `07_Методика_испытаний.md`, а фактически
полученные результаты — в каталоге `results/`.
