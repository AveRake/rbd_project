# 5. Физическое проектирование и реализация БД

## 5.1. Требования к операционной обстановке

**Оценка объёма данных.** Объём внешней памяти складывается из памяти под
модули СУБД и памяти под данные. Оценим память под данные (МД) на первый год
работы, исходя из ориентировочных объёмов (см. ТЗ).

| Таблица | Кол-во записей | Средний размер записи | Объём |
|---|---|---|---|
| equipment_units | 20 000 | 150 байт | 3,0 МБ |
| rentals | 15 000 | 120 байт | 1,8 МБ |
| requests | 6 000 | 200 байт | 1,2 МБ |
| request_items | 15 000 | 100 байт | 1,5 МБ |
| contracts | 5 000 | 120 байт | 0,6 МБ |
| payments | 8 000 | 90 байт | 0,7 МБ |
| universities / departments / representatives | 1 700 | 250 байт | 0,4 МБ |
| models / tariffs / НСИ | ~4 000 | 150 байт | 0,6 МБ |
| maintenance / transfers | 5 000 | 120 байт | 0,6 МБ |
| **Итого данные** | | | **≈ 10,4 МБ/год** |

С учётом индексов и служебных структур применим коэффициент 2–3:
**МД ≈ 30 МБ/год**. СУБД и журналы занимают порядка 1 ГБ.

**Вывод:** объём данных невелик, специальных требований к объёму внешней и
оперативной памяти не предъявляется. Достаточно:

- серверы БД — 2 vCPU, 2–4 ГБ ОЗУ, диск 20 ГБ SSD (с запасом на журналы
  репликации и резервные копии);
- клиентские места — любой ПК с браузером;
- операционная система — Linux (Debian/Ubuntu) с Docker и Docker Compose.

## 5.2. Выбор СУБД и программных средств

Для реализации выбрана **MySQL 8.0** (в контейнерах Docker). Обоснование:

- поддержка реляционной модели и всех необходимых ограничений целостности
  (внешние ключи, уникальные и проверочные ограничения, триггеры, представления);
- встроенная поддержка **репликации** в режимах master/slave и консолидации
  (каналы репликации) — ровно те механизмы, которые требуются по заданию;
- соответствие методическим указаниям (примеры настройки приведены именно для
  MySQL 8.0 с Docker Compose);
- свобода использования и распространённость.

Дополнительные средства:

- **Docker / Docker Compose** — развёртывание нескольких узлов СУБД на одной
  машине (учебный стенд);
- **phpMyAdmin / DBeaver / DataGrip** — клиенты администратора;
- **PHP/JavaScript (HTML)** — демонстрационный интерфейс (по методическим
  указаниям допускаются простые решения).

## 5.3. Схема хранения и доступа

- Все отношения создаются в кодировке `utf8mb4` с движком `InnoDB` (поддержка
  транзакций и внешних ключей, необходимых для распределённых транзакций).
- Для всех внешних ключей создаются индексы (в InnoDB индексы по внешним ключам
  могут создаваться автоматически, но для составных и часто используемых полей
  индексы заданы явно).
- Дополнительные индексы создаются по полям, участвующим в частых запросах:
  инвентарный номер, статус и модель экземпляра, период аренды, ИНН вуза,
  логин сотрудника.

Код создания объектов приведён в каталоге `sql/`:

## 5.4. Представления (готовые запросы)

Материализация доступа реализуется через представления (см. `sql/04_views.sql`).
Ключевые представления:

1. `v_available_equipment` — свободная техника по филиалам;
2. `v_current_rentals` — текущие (невозвращённые) выдачи;
3. `v_overdue_rentals` — просроченные возвраты;
4. `v_branch_load` — загрузка парка филиала;
5. `v_consolidated_fleet` — сводный парк по филиалам (консолидированная копия);
6. `v_my_branch_requests`, `v_my_university_requests`, `v_my_university_contracts`
   — представления с фильтрацией по пользователю и `WITH CHECK OPTION` для
   разграничения доступа.

## 5.5. Триггеры (реализация ограничений целостности)

Список триггеров и контролируемых ими ограничений (см. `sql/05_triggers.sql`):

| Триггер | Ограничение |
|---|---|
| `trg_req_check_branch` | филиал заявки совпадает с обслуживающим филиалом вуза |
| `trg_req_check_dep` | подразделение и представитель принадлежат вузу заявки |
| `trg_rit_check_tariff` | тариф соответствует модели позиции |
| `trg_rit_check_period` | период позиции не выходит за период заявки |
| `trg_rental_check_available` | выдаваемый экземпляр свободен и его модель соответствует позиции |
| `trg_rental_check_overlap` | выдачи одного экземпляра не пересекаются по времени |
| `trg_rental_set_status_out` | при выдаче статус экземпляра → 'аренда' |
| `trg_rental_set_status_in` | при возврате статус экземпляра → 'свободна', фиксируется состояние |
| `trg_request_check_sum` | сумма позиций равна `REQ_SUM` |
| `trg_contract_check_sum` | сумма договора равна сумме выдач |
| `trg_tariff_period` | запрет пересечения периодов действия тарифов одной модели и единицы |

## 5.6. Права доступа

Роли СУБД создаются командой `CREATE ROLE`, права назначаются `GRANT`
(см. `sql/07_users_grants.sql`). Перечень ролей: `br_manager`, `storekeeper`,
`service`, `br_head`, `univ_rep`, `hq_spec`, `hq_boss`, `accountant`.

Примеры назначения прав:

```sql
GRANT SELECT, INSERT, UPDATE ON campusrent.universities TO br_manager;
GRANT SELECT, INSERT, UPDATE, DELETE ON campusrent.equipment_units TO storekeeper;
GRANT SELECT ON campusrent.v_my_university_requests TO univ_rep;
GRANT SELECT, INSERT, UPDATE, DELETE ON campusrent.payments TO accountant;
GRANT ALL PRIVILEGES ON campusrent.* TO hq_spec;
```

Права представителей вузов и руководителей филиалов назначаются через
представления с фильтрацией по `user()` и `WITH CHECK OPTION`, что не позволяет
им изменить «чужие» данные.

## 5.7. Стратегия резервного копирования

Интенсивность обновления БД умеренная, объём данных невелик. Применяется:

- **полное резервное копирование** каждой БД узла один раз в сутки (например,
  `mysqldump` по расписанию, перед завершением рабочего дня);
- для узла ЦО дополнительно **инкрементное** копирование журналов бинарных
  логов (они и так ведутся для репликации);
- хранение резервных копий — не менее 7 суток; одна из копий выносится на
  отдельный носитель;
- периодическая **проверка восстановления** на тестовом стенде.

Пример задания резервного копирования (cron на узле):

```cron
0 20 * * * mysqldump --single-transaction --routines --triggers \
  -uroot -p"$MYSQL_ROOT_PASSWORD" campusrent > /backup/campusrent_$(date +\%F).sql
```

Консолидированная копия ЦО также играет роль резервной копии для филиалов.
