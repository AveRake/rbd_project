# Протокол распределённой транзакции РТ-1 (межфилиальное бронирование)

Сценарий: `docs/04_Схема_фрагментации.md`, п. 4.7, РТ-1.
Реализация: `replication/distributed_booking.sh`.
Стенд: MySQL 8.0 в Docker, четыре узла (`replication/setup.sh`).
Дата прогона: 11.10.2026.

**Постановка.** Филиалу Санкт-Петербург нужен экземпляр модели, свободных
экземпляров которой в СПб мало, — он есть на складе филиала Казань.
Бронирование должно быть атомарным: либо экземпляр помечен «бронь» **и** в СПб
создана заявка с позицией, либо не происходит ничего.

**Роли узлов.**

| Узел | Роль в транзакции | Что делает |
|---|---|---|
| `mysql-slave` (SPB) | координатор | создаёт заявку `requests` и позицию `request_items` |
| `mysql-slave2` (KZN) | участник (владелец техники) | переводит экземпляр в статус «бронь» |
| `mysql-consol` | узел консолидации | проверка результата (РКД) |

**Метод.** Протокол двухфазной фиксации на основе XA-транзакций MySQL:
фаза 1 — `XA START … XA END … XA PREPARE` на каждом узле, фаза 2 — `XA COMMIT`
на всех узлах после подтверждения готовности. Подготовленная транзакция
переживает обрыв соединения и видна в `XA RECOVER`; до фиксации её изменения
не видны другим сеансам.

## Ход выполнения

| Шаг | Действие | Фактический результат |
|---|---|---|
| 1 | Автоматический выбор экземпляра | `EQ_ID=100495`, `KZN-00100495`, модель 401 (Keysight DSOX1204G); свободно в СПб — 2 шт., в Казани — 5 шт. |
| 2 | Фаза 1, участник KZN: `XA START`, `UPDATE equipment_units SET EQ_STATUS='бронь' WHERE EQ_ID=100495 AND EQ_STATUS='свободна'`, `XA END`, `XA PREPARE` | `PREPARED`; из другого сеанса статус по-прежнему `свободна` — изменение не опубликовано |
| 3 | Фаза 1, координатор СПб: `XA START`, `INSERT` заявки и позиции, `XA END`, `XA PREPARE` | `PREPARED`, новая заявка `REQ_ID=500526`; в другом сеансе заявок по-прежнему 263 |
| 4 | Проверка готовности: `XA RECOVER` на обоих узлах | `campusrent_book_kzn_20261011194050` и `campusrent_book_spb_20261011194050` |
| 5 | Фаза 2: `XA COMMIT` на участнике, затем на координаторе | транзакция зафиксирована на обоих узлах |
| 6 | Проверка результата | `EQ_ID=100495` → `бронь`; заявка `XA-500526` (`СПбГУ`, филиал `SPB`, статус «подана», сумма `31 080.00`) |
| 7 | Проверка консолидации (РКД) | в консолидированной копии `mysql-consol` экземпляр `100495` имеет статус `бронь` |
| 8 | Негативная проверка: повторное бронирование того же экземпляра | `NOT_FREE` — `UPDATE` не затронул ни одной строки, транзакция откачена (`XA ROLLBACK`), лишняя заявка не создана |
| 9 | Состояние каналов репликации | 6 из 6 каналов `Yes`, `Last_Error` пусто |

Факт шага 2 — ключевое доказательство корректности двухфазной фиксации:
строку изменил только участник, но до `COMMIT` её никто не видит.

## Ограничения MySQL 8.0, определившие реализацию

1. **XA-команды недоступны через `PREPARE`** (ошибка 1295 «This command is not
   supported in the prepared statement protocol»), а XID в `XA START` должен
   быть литералом. Поэтому каждая фаза оформлена хранимой процедурой, в текст
   которой XID подставляется при создании.
2. **XA несовместима с фильтрами репликации** (ошибка 3898 «The use of
   replication filters with XA transactions is not supported»). На стенде
   каналы фильтруются (`replicate-do-table`): ЦО принимает только таблицы
   клиентов, узел консолидации — только операционные. Поэтому:
   * **участником** выбран филиал Казань: его бинарный журнал читает только
     узел консолидации, и таблица `equipment_units` входит в его фильтр —
     XA проходит, изменение видно в консолидированной копии (шаг 7);
   * **транзакция координатора** меняет `requests`/`request_items`, которые ЦО
     фильтром исключает, поэтому она выполняется с `SET sql_log_bin = 0` —
     локально для филиала, без передачи в репликацию. Атомарность от этого не
     страдает: её обеспечивают фазы XA на двух узлах, а не репликация.
3. **Вспомогательные процедуры — это DDL**, а `log_replica_updates` в MySQL 8.0
   включён по умолчанию: незакрытый DDL разнёсся бы по каналам и остановил
   узел, где такой объект уже есть (ошибка 1304). Поэтому создание и удаление
   процедур выполняется с `SET sql_log_bin = 0`. После прогона проверено: ни
   на одном узле не осталось ни временных процедур, ни незавершённых
   XA-транзакций (`XA RECOVER` пуст).

## Воспроизведение

```bash
cd replication
bash setup.sh                 # если стенд ещё не поднят
bash distributed_booking.sh   # полный прогон (~15 секунд)
```

Дословный вывод прогона — в `distributed_booking_log.txt`.
